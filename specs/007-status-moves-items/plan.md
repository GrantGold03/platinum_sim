# Implementation Plan: Status Moves and Held Items in Team Optimization

**Branch**: `007-status-moves-items` | **Date**: 2026-10-14 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/007-status-moves-items/spec.md`

## Summary

The optimizer will offer status moves, variable-power attacks and every useful held item as candidates, and judge them with a battle player that understands them.

1. **Classification.** Moves are classified from the decomp's per-effect battle scripts. Foe drops, fixed damage, no-effect, sacrifice and reactive moves are excluded, each with a recorded reason. Held items are filtered by whether battle code references their hold effect, then paired with the moves they strengthen (research R1-R3).
2. **Player.** `expectimax2` gains a v3: weather, Leech Seed, Substitute, hazards, Taunt/Encore/confusion, Baton Pass, the remaining items, and a leaf value that sees residual damage. It is built **reference-first**: an exact, expensive `-v3-ref`, then cheaper settings accepted only if they aren't worse. v1 and v2 stay byte-identical (R4).
3. **Optimizer.** A new `alternatives` stage replaces the setup check. It tests each member's status/item alternatives on paired seeds near the clear threshold, repairs copy conflicts, controls for multiple comparisons and confirms each winner. It has a `reference` mode with no limit and a `prefilter` mode accepted against it (R5).
4. **Required HMs.** Adopted moves are protected from HM placement (R6).
5. **Ledger.** It gains the Route 221, Pastoria and Amity Square item sources (R7).
6. **Reporting.** Every offered, tested and adopted candidate is reported, with "not modelled" warnings (R10).
7. **Benchmark.** Five benchmark teams with a measured baseline judge the result (R9).

## Technical Context

**Language/Version**: Python ≥ 3.14 (uv); Node 22 (`sim/`, the policy and worker)

**Primary Dependencies**: existing only (FastAPI, uvicorn, openpyxl; vendored Pokemon Showdown and the pokeplatinum decomp). No new dependencies.

**Storage**: files (`runs/<job>/state.json`, report files, `data/generated/*.json` regenerated by `platsim extract`)

**Testing**: `uv run pytest` (unit, integration, browser); `node --test sim/test`; golden log-hash tests for v1/v2; paired McNemar benchmarks

**Target Platform**: local Linux, 16 workers (Ryzen 7 5700X3D), offline

**Project Type**: CLI plus local web app, with a Node battle worker

**Performance Goals**:
- **every** one-time run of this feature: at most 100 h in total (spec FR-017 table: suites 8, baseline 11, player 15, generation and item references 8, screening check 3, candidate reference on B4/B5/B3 31, final prefilter benchmark 22, SC-002 evaluations 2). Round sizes are fitted to the measured number of alternatives (research R5). A running total is kept in `validation-log.md`;
- **hard maximum:** the accepted prefilter takes at most 2.0× the measured `f88cdd0` baseline per standard run, per team (FR-017, SC-006, user 2026-10-14);
- the production v3 player decision time is recorded against v2's 37-49 ms.

**Constraints**:
- Constitution I-VI;
- v1 and v2 player output unchanged;
- deterministic results (SC-005);
- validator independent and unchanged in logic;
- local compute only.

**Scale/Scope**:
- 98 final forms;
- 130 status-move effects and 147 hold effects classified;
- about 87 items offered under default options;
- a probe counted 5,600-9,600 1-2-slot alternatives per team before items and before dropping unmodelled moves (analysis C1). Reference mode screens them by successive halving, with round sizes fitted to the 100 h budget; the real N per team is measured first;
- 5 benchmark teams.

## Constitution Check

*GATE: checked before Phase 0, re-checked after Phase 1.*

| Principle | How the design complies | Status |
|---|---|---|
| I. Decomp is ground truth | Move categories are derived from `ES` scripts and subscript pointers. Item relevance comes from hold-effect references in battle code. Pairings come from effect scripts and battle code. Variable powers use decomp formulas, with weights extracted from `res/pokemon`. Ledger sources are extracted from scripts and C tables. The unavoidable rule table (about 20 entries) is keyed on decomp constants, never move names, and guarded by completeness tests. | PASS |
| II. Showdown is the battle engine | Showdown isn't modified. Every battle is still simulated by Showdown. The player's internal model is used only to choose our side's actions, which is not battle simulation, so extending it doesn't reimplement the engine. A mechanics-divergence pass over every offered effect and item records each disagreement in `data/divergences.json` (Encore first). A test checks that every offered item maps to Showdown. Every result names the player version. | PASS |
| III. Legality | The validator logic is unchanged and still runs on every output. Copy limits come from `team_item_copies`. The new ledger sources follow the existing phase rules, and the validator accepts their items exactly when the ledger does. | PASS |
| IV. Reproducible, honest evaluation | New seed namespace `|alternatives`. Paired McNemar with Holm correction and a fresh-seed confirm. A golden test pins v1/v2. `STATE_VERSION` 4. The mode and policy are in the fingerprint and provenance. The objective is unchanged and stated. | PASS |
| V. Positive controls | Controls for every category (R1), item filter (R2), variable power (R3), player mechanic (SC-008), ledger source (R7) and exclusion (SC-007). Negative results such as "not adopted" come with test records. | PASS |
| VI. Reference-first | Player: `-v3-ref` first, cheap settings accepted against it. Candidates: `reference` mode first, `prefilter` accepted against it. The 1-2-slot generation cap is validated by a 3-slot reference on two members. Results and run times go in the validation log. | PASS, with one recorded cap (Complexity Tracking) |

**Post-design re-check (after data-model and contracts):** unchanged, all PASS. The `setup_moveset` removal and the `MemberSpec.adopted` field don't affect the principles.

## Complexity Tracking

| Item | Why needed | Simpler alternative rejected because |
|---|---|---|
| Rule table of about 20 decomp constants in `move_classes.py` / `item_classes.py` | Some meanings can't be derived from scripts: sacrifice moves, Follow Me, the Curse split, no-outcome items | A fully derived rule misclassifies them. A move-name list violates Principle I. Guarded by completeness tests. |
| Candidate generation = 1-2-slot substitutions plus structured 3-4-status sets (one move per category) | Full 3-4-slot generation is infeasible (Blissey alone has about 15,000 3-slot sets) | Principle VI: validated against full 3-4-slot generation on B4 Milotic and Roserade. If a full-generation set wins significantly, the rule is widened (user, 2026-10-14, analysis I1). |
| Reference mode screens by successive halving before the full test, with round sizes fitted to a 100 h total budget | A flat full test is about 115-196 h per team, and generous rounds about 160 h per team (analysis C1) | User decisions C1(a) and the 100 h budget. Every offered alternative still reaches the strong player. **Unverified** until T066b checks it against a full test of a sample of alternatives on one member (Constitution VI). |
| Items offered only with their paired moves (FR-009 relevance filter) | Offering every item with every moveset multiplies the alternatives | Checked in T066 against offering every allowed item on two members; unverified until then. |
| Two player configurations (`-v3-ref` and `-v3`) and two optimizer modes kept long-term | Principle VI requires the reference to stay available for re-checking | Deleting the reference would leave the cheap version unverifiable after later changes |
| The `alternatives` stage replaces the setup check | The setup check skips unbuildable sets, ignores paired items, has no multiplicity control and compares far above the threshold | Patching it in place would keep the fixed-level comparison that judges level-deficit strategies in the wrong regime |
